## 三、面试 Q&A 高频问题（含参考回答）

### Q1：什么是 RAG？为什么用它而不用微调？

RAG 是"检索增强生成"，生成前先从外部知识库检索相关片段作为参考，再让大模型基于资料回答。选择它是因为：(1) 垂直领域知识更新频繁，微调一次成本高且需要 GPU 和标注数据；(2) RAG 知识库可随时增删文档，无需重训；(3) 回答可追溯引用来源，比微调更容易控制幻觉。

### Q2：向量检索和 BM25 各有什么优缺点？

向量检索把文本映射为语义向量，用余弦相似度衡量语义相关性，能处理同义改写，但精确词面匹配弱；BM25 是基于词频/逆文档频率的经典统计检索，精确匹配强但不懂语义。所以我用 RRF 融合二者，取长补短。

### Q3：RRF 融合的原理是什么？

RRF（Reciprocal Rank Fusion）是基于**排名**而非分数的融合：对每个文档，累加其在各检索结果中的 1/(k+rank)，k 通常取 60。好处是不需要归一化不同检索器的分数，实现简单、鲁棒性强。

### Q4：如何切分文档？为什么？

用"递归字符切分"：优先在段落边界切，其次句子、再次标点，最后才按字符硬切；相邻块保留重叠窗口防止上下文断裂。这样 chunk 内部语义尽量完整，检索质量更高。参数（chunk_size=500、overlap=80）通过实验调优。

### Q5：怎么解决大模型的幻觉？

三层机制：一是系统提示词限定"只能依据参考资料回答"；二是资料不足时要求明确拒答；三是回答强制标注 [n] 引用编号，前端可点击查看原文。用户能校验，模型也不敢乱编——数据上可用忠实度指标评估。

### Q6：数据库和向量库如何保证一致性？

文档入库时先写向量库、再写 SQLite 并同步状态；删除文档时先删向量再删记录；知识库删除时整体删除向量集合；文档级操作幂等（重新解析前先清理旧向量）。因此不会出现"SQLite 有记录但向量缺失"的孤儿数据。

### Q7：Embedding 用什么模型？维度多少？

默认用云端 bge-m3（1024 维）或本地 bge-small-zh（512 维），都是中文效果较好的开源模型；离线演示模式用哈希伪向量跑通流程。选择 API 方式是因为无 GPU 环境也能高质量向量化。

### Q8：系统性能如何？有哪些瓶颈？

瓶颈在三个地方：文档解析（PDF 大文件耗时）、Embedding 批量请求、LLM 生成延迟。优化：解析入库走后台任务、Embedding 批量 32 条并发、问答用流式输出降低首字延迟。当前单机支撑个人/小组使用完全足够。

### Q9：如果知识库里没有答案怎么办？

系统会拒答并提示"根据现有资料无法回答"，同时引导用户补充文档。这既是功能设计，也是防止幻觉的手段。

### Q10：这个项目最困难的部分是什么？

（建议结合真实开发经历回答，示例）最困难的是混合检索调优——刚开始只用向量检索，发现精确型号类问题召回差；加入 BM25 后分数量纲不同无法直接合并，调研后采用 RRF 排名融合解决；再用一组人工标注的问答对做消融实验验证了提升。
