## 第一部分：30 秒电梯陈述（答辩开场背熟）

> 我的毕业设计题目是《基于大语言模型的智能领域知识问答系统》。
>
> 它的核心思路是 RAG——检索增强生成。传统大模型回答垂直领域问题时有两个痛点：一是专业知识不足，二是会产生幻觉、编造答案。我的方案是：**先检索、后生成**。用户上传 PDF、Word 等文档后，系统把文档解析、切分、向量化，存入本地向量数据库 ChromaDB；用户提问时，系统先从知识库检索最相关的文档片段——这里我做了混合检索，向量语义检索和 BM25 关键词检索通过 RRF 算法融合，再把检索到的资料和问题一起拼成 Prompt 交给大模型，让它**只依据资料回答并标注引用编号**，最后通过 SSE 流式返回，用户能看到逐字输出的效果。
>
> 整个系统是我自主实现的 RAG 管线（Loader → Splitter → Embedder → Retriever → Generator → Pipeline），没有依赖 LangChain 这类框架，共 6 张数据库表、14 个 REST 接口，并且做了双模式设计——没有 API Key 也能离线跑通全流程，有 Key 就接入真实大模型。这个项目我完成了从架构设计、数据库设计、前后端实现到端到端测试的全部工作。

（约 60 秒，节奏：痛点 → 方案 → 我的实现 → 量化成果）

## 第三部分：核心链路逐段拆解（代码级）

### 3.1 文档解析（loader.py）

**回答要点**：按扩展名分发到三个解析器，输出"段落块"列表 `[{text, meta:{page, heading}}]`，保留段落边界供后续切分。

- **PDF**（`_parse_pdf`，33-55 行）：用 `pypdf` 逐页 `extract_text()`，每页文本清洗后作为一个 block，`meta.page` 记录页码。**如果提取不到文本（扫描件）会直接报错提示用 OCR 版本**——这是健壮性设计。
- **DOCX**（`_parse_docx`，58-91 行）：遍历段落，**通过样式名识别标题**（`heading` / `标题`），标题存入 `meta.heading`，作为后续 chunk 的"小节归属"；正文段落继承当前最近标题。段落为空时兜底解析表格（`|` 拼接单元格）。
- **MD/TXT**（`_parse_text`，94-111 行）：**UTF-8 失败自动降级 GBK**（解决 Windows 常见中文编码问题）；`#` 开头识别为标题。
- `_clean`（114-118 行）：清理全角空格、BOM、空行。

> 老师可能追问：**"PDF 解析出来是纯文本，你怎么知道它是哪一节的？"**
> 答：PDF 无结构化标题信息，所以 PDF 的 heading 为 None，靠 `meta.page` 溯源；DOCX/MD 有标题结构才记录 heading。这是解析器的现实约束，也是我下一步可优化的点（如对 PDF 做版式分析）。

### 3.2 文本切分（splitter.py）

**回答要点**：中文优化的递归字符切分。分隔符优先级 `["\n\n", "\n", "。", "！", "？", "；", "，", " ", ""]`，即**段落 → 句子 → 标点 → 字符**逐级降级。

核心逻辑（`split_text`，18-43 行）：
1. 文本总长 ≤ 500 直接整块返回；
2. 否则在 `window = text[:500]` 内，**从后往前**找优先级最高的分隔符位置 `cut`（`_find_cut_point`，46-57 行，且要求 `pos > 250` 避免切分点过前产生过多碎块）；
3. 切出一块后，`remaining = remaining[cut:]`，**再吃掉 overlap=80 个字符**（39-42 行），即下一块从重叠处开始，保证跨切分点的语义内容不丢失；
4. 循环直到切完，`seq` 全局递增编号（`split_blocks`，60-74 行）。

> 老师可能追问：**"overlap 的作用？为什么是 80？"**
> 答（重点！）：overlap 用于补偿"一刀切"造成的上下文断裂——比如一句话跨在两个 chunk 上，如果没有 overlap，前后各缺一半，检索命中时上下文不完整。80 = 500 的 16%，处于业界常规的 10%-20% 区间。**overlap 不是越大越好**：重复内容会导致向量库冗余、同一信息点出现在多个 chunk 稀释检索精度，而且 embedding 按 token 计费，冗余直接增加成本。80 是"上下文连续性"与"存储/成本冗余"之间的平衡点。（**注意：代码实际值是 80，答辩时务必说 80，不要说 200。**）

### 3.3 向量化（embedder.py）

**回答要点**：统一接口 `embed(texts) -> list[list[float]]`，三种实现：

- **APIEmbedder**（29-60 行）：调 OpenAI 兼容 `/embeddings` 接口，**批量 32 条/次**，超时 60s；`model = BAAI/bge-m3`，输出 1024 维；按 `index` 排序保证返回顺序与输入一致。
- **HashEmbedder**（63-84 行）：零依赖离线方案。取文本字符 **1/2/3-gram 集合**，每个 gram 用 MD5 哈希映射到 256 维的某个位置，**带符号计数**（`h[4]` 奇偶决定 ±1），最后 **L2 归一化**。确定性哈希保证"相似文本 → 向量相近"，用于无 Key 环境跑通全流程。
- **LocalEmbedder**（87-103 行）：sentence-transformers 本地推理，可选依赖。

> 老师可能追问：**"为什么 embedding 要走 API 而不是本地？"**
> 答：我的机器是无独显的轻薄本（Iris Xe 集显），本地跑 bge-m3 一个文档要几十秒且占内存；API 方案批量 32 条并发、单文档秒级完成，质量也更高。**重算力上云、轻逻辑本地**是我整个项目遵循的架构原则。同时我保留了 LocalEmbedder 实现，证明这条路也走过、评估过。

### 3.4 向量入库（retriever.py add_chunks，54-76 行）

**回答要点**：
- 每个知识库一个 collection，命名 `kb_{id}`，创建时指定 `metadata={"hnsw:space": "cosine"}`（37 行）——告诉 ChromaDB 用余弦距离做近邻搜索；
- 向量 id 格式 `kb{id}_c{seq}_{i}`（57 行），**与 SQLite 的 Chunk.vector_id 字段对应**，是两库关联的桥梁；
- 写入**每批 200 条**（69 行），避免单次请求体过大；
- metadata 携带 `kb_id / doc_id / seq / heading / page`，检索结果可直接溯源到原文页码。

### 3.5 检索（retriever.py search，89-131 行）

**回答要点**（这是全项目最核心、答辩必问的模块）：

```
1. query 向量化（embed_one）
2. 向量检索：ChromaDB query，取 top_k×2 = 10 个候选（105-122 行）
   → score = 1 - cosine_distance（120 行，ChromaDB 返回距离，转相似度）
3. BM25 检索：自实现打分，同样取 10 个候选（124-127 行）
4. RRF 融合：两个列表按排名加权，取 top_k×3 = 15 个候选（130 行）
5. 噪音过滤：目录页/声明页/致谢页/短文本 → 最终 top_k = 5（131 行）
```

**为什么要多取候选再融合**（105 行注释）：RRF 只看**排名**不看分数，如果向量和 BM25 都只取 5 个，两边都命中的内容排名会很高，但可能漏掉"只在一边排名第 6-10 但有价值"的内容。多取 2 倍候选，融合更充分。

**噪音过滤**（`_filter_noise`，133-163 行）：这是为学位论文类文档设计的优化——目录页（大量 `....`/`……` 页码引导符）、声明页/授权书/致谢页（前 120 字关键词前缀匹配）、过短文本（<30 字）都会被过滤，避免污染检索结果；过滤后不足 top_k 时从原始结果补足，保证不丢内容。

> 这个优化是有真实 bug 驱动出来的（可讲个故事）：处理师姐的毕业论文时，问"引用了哪些文献"���系统把"目录页""原创性声明"检索到前面，真正的参考文献页被挤出 top5。后来加了点号密度检测 + 关键词前缀过滤才解决。**这是写在论文"系统优化与改进"章节的真实工���案例。**

### 3.6 BM25 自实现（retriever.py _bm25_search，166-217 行）

**回答要点**：
- 用 `col.get(include=["documents","metadatas"])` 全量拉取当前 collection 的文档（**规模小时可行，是演示级权衡**）；
- 每篇文档和 query 都用 **jieba 分词 + 去停用词**（`_tokenize`，220-224 行，去掉"的/了/是/在/和/与"）；
- 统计文档频率 df、文档总数、平均长度；
- 每个查询词 t：`idf = ln(1 + (N - df + 0.5)/(df + 0.5))`（**平滑版 IDF，避免除零**，201 行）；`score += idf × tf·(k1+1) / (tf + k1·(1 - b + b·len/avgdl))`（202 行）；
- 超参数 k1=1.5（词频饱和控制，抑制"词出现 100 次就比 10 次强 10 倍"），b=0.75（长度归一化强度，抑制长文档天然词频高）。

### 3.7 RRF 融合（retriever.py _rrf_fusion，227-253 行）

**回答要点**：
- 对每个候选 chunk（以 vector_id 为键），在两个列表中的**排名**分别贡献 `1/(K + pos + 1)` 分（pos 从 0 计，236 行）；
- 两边都命中的 chunk 得两分，排名越靠前分越高；
- 按总分排序取 top_k。K=60。

### 3.8 Prompt 组装（prompts.py）

**回答要点**：
- `SYSTEM_PROMPT`（6-14 行）：五条硬约束——只能依据参考资料回答、资料不足要明说、**句末标注引用编号 [1][2]**、中文分点、闲聊引导回正题。这是"防幻觉 + 可溯源"的提示词层保障。
- `build_qa_messages`（17-53 行）：**历史只取最近 6 条**（29 行），每条截断到 300 字（44 行），控制上下文长度（GLM-4-Flash 上下文 128K，但 RAG 场景保留最近几轮即可，省 token 且聚焦）；参考资料按 `[1] 内容（来源：xxx，第N页）` 格式拼装（32-37 行），**页码信息让 LLM 能给出带位置的引用**。

### 3.9 LLM 生成 + SSE（generator.py + pipeline.py + chat.py）

**回答要点**：
- `LLMClient` 封装 OpenAI 兼容接口，**同一个类两种模式**：`api` 调真实模型，`echo` 返回模拟答案（31-35 行属性判断）。
- 流式（58-97 行）：POST `/chat/completions` 带 `stream: true`，用 `httpx` 异步流式读响应，解析 `data:` 前缀的 SSE 行，`[DONE]` 结束，逐段 yield 内容。**如果某行解析失败直接 continue 跳过**（96-97 行），保证一个坏包不中断整条流。
- `answer_stream`（pipeline.py 113-196 行）是事件编排器，产出四类事件：`sources`（检索到的引用，每条截 400 字）→ `delta` × N（流式文本）→ `done`（含 conversation_id/message_id）→ `error`。**用户消息和助手消息都在流结束后落库**（144-183 行），消息的 `sources` 字段存 JSON，前端可以回看引用。
- 路由层（chat.py 104-122 行）：`StreamingResponse(media_type="text/event-stream")`，每事件 `data: {json}\n\n` 格式。

> 老师可能追问：**"SSE 和 WebSocket 为什么选 SSE？"**
> 答：RAG 问答是**单向**数据流（服务器 → 客户端），SSE 恰好够用且实现简单：基于 HTTP，断线可用 EventSource 自动重连；而 WebSocket 需要协议升级、心跳保活、双向消息处理，复杂度更高，本项目没有客户端持续上报的需求。另外 OpenAI 官方流式接口本身就是 SSE，我这边直接解析透传，语义一致。**如果未来要做"生成中可打断/重新生成"，WebSocket 或 Fetch 流式读 + AbortController 更合适**（前端现在用的是 fetch + ReadableStream，支持中断）。

## 第四部分：三个核心算法公式（必须能手推）

### 4.1 余弦相似度（Cosine Similarity）

用于衡量两个向量的"方向一致性"，值域 [-1, 1]：

```
                A · B         Σ(aᵢ × bᵢ)
cos(θ) = ─────────────── = ─────────────────────────
           ‖A‖ × ‖B‖     √Σaᵢ² × √Σbᵢ²
```

- 语义：文本 → 向量后，语义相近的文本向量夹角小，余弦值接近 1。
- **为什么选余弦不选欧氏距离**：向量 norm 反映文本长度/活跃度，语义主要藏在**方向**里；余弦对向量长度做了归一化，与文本长度解耦，更适合 embedding 检索。
- 代码位置：ChromaDB 的 collection 以 `hnsw:space=cosine` 创建，返回 `distance`，代码转相似度：`score = 1 - distance`（retriever.py:120）。bge-m3 的 embedding 本身做了归一化（模长为 1），此时余弦相似度 = 点积。
- 手推例子：A=(1,2)，B=(3,1)。A·B=1×3+2×1=5；‖A‖=√5，‖B‖=√10；cos=5/√50≈0.707。

### 4.2 BM25（Best Matching 25）

对文档 d 与查询 q，打分公式：

```
BM25(d, q) = Σ   IDF(t) × ────────────────────────────
             t∈q           f(t,d) + k₁(1 - b + b·|d|/avgdl)
```

其中：

- `f(t,d)`：词 t 在文档 d 中的词频；
- `|d|`：文档长度（词数），`avgdl`：语料平均长度；
- `IDF(t) = ln(1 + (N - df(t) + 0.5) / (df(t) + 0.5))`（**+0.5 平滑，防止 df=N 时除零/负值**）；
- `k₁ = 1.5`：**词频饱和系数**。f 越大，分子分母同增，得分趋近饱和上界 `k₁+1` 倍 IDF——意思是"出现 100 次并不比 10 次强 10 倍"，抑制高频词过拟合；
- `b = 0.75`：**长度归一化强度**。b 越大，长文档的得分惩罚越强，防止长文档因词数多而天然占优。b=0 时完全忽略长度。

**直觉**：一个词既要在文档里出现得多（词频高）、又要在整个语料里稀有（IDF 大），才是好匹配。专有名词、编号、型号这类词 BM25 抓得准——这正是纯向量检索的弱项。

### 4.3 RRF（Reciprocal Rank Fusion，倒数排名融合）

对每个文档 d，融合分 = 它在**每个检索器结果列表中的排名**的倒数加权和：

```
                  1
RRF(d) = Σ  ───────────
         r∈R  k + r(d)
```

- `r(d)`：文档 d 在某个检索器结果中的排名（1 起）；
- `k = 60`：常数（**Cormack et al., 2009 论文中验证的经验值**，后续无监督融合研究普遍沿用）；
- 只使用**排名**，不使用原始分数——因为向量相似度和 BM25 得分**量纲不同、不可直接相加**（一个是 0~1 的余弦，一个是无界的 BM25 分数），RRF 把它们统一到排名空间再融合，这是它最优雅的地方。

**k=60 的影响**（答辩必问）：
- k 越小，排名越靠前的文档权重差异越尖锐（第 1 名 1/61，第 2 名 1/62，衰减快），融合结果越"激进"；
- k 越大，各名次权重差异越平缓，结果越接近"两个检索器都命中的文档优先"；
- k=60 时相邻名次权重差约 0.02%，衰减温和，**既保证高分文档有优势，又不让单一检索器的头部结果垄断融合结果**。60 是经过多数据集验证的通用值，我用它避免过拟合调参。

**一个数说明融合效果**：文档在向量检索排第 1（1/61≈0.0164）、BM25 排第 3（1/63≈0.0159），总分 0.0323，可能超过"向量排第 2 但 BM25 没命中"的文档（1/62≈0.0161）。**两边都命中的文档有结构性优势**。

## 第五部分：关键设计决策 12 问（答辩必背）

### Q1. 为什么用 ChromaDB 不用 FAISS？

> FAISS 是**向量索引库**，不是**向量数据库**：它只管"索引 + 最近邻搜索"，没有内置的元数据管理、持久化语义、collection 隔离和按元数据过滤。用它做 RAG 应用，我还要自己实现：索引落盘与加载、chunk 与索引的 id 对应关系、按知识库隔离、按 doc_id 删除等。
> ChromaDB 是**嵌入式向量数据库**：内置 HNSW 索引（和 FAISS 同量级的 ANN 算法）、SQLite 落盘持久化、collection 概念天然对应"一个知识库一个集合"、支持 metadata 过滤和按 id 增删。API 一行 `col.add(...)` / `col.query(...)` 就完成写入检索，**显著降低工程复杂度，而且单机嵌入式零部署**，完全匹配毕设演示场景。
> 补充防守：如果老师问"数据量大怎么办"——我的 Retriever 接口是抽象的，未来可平滑替换为 Milvus/Weaviate，不影响上层。**选型逻辑是：索引能力等价，ChromaDB 多给了元数据管理，符合项目规模。**

### Q2. 为什么 chunk_size=500，overlap=80？

> - 500 字符（中文约 300 字左右 token）是一个经验平衡点：**太小**（如 100）→ chunk 语义不完整、检索碎片化、token 上下文被大量 chunk 挤占；**太大**（如 2000）→ 单块主题混杂、向量语义被稀释、命中不精准、LLM 上下文窗口浪费。
> - overlap=80（16%）用于补偿切分点切断语义：一句话跨两块时不丢上下文。**不是越大越好**：重复内容造成向量库冗余、同一信息点多份拷贝稀释检索精度、embedding 按 token 计费增加成本。业界常规 10%-20%，80 取中。
> - 这两个值都在 `config.py` 里可配置（环境变量覆盖），答辩可以补一句"我把它设计成可调参数，方便实验对比不同切分粒度"——呼应论文里的消融实验设计。

### Q3. 为什么 RRF 的 k=60？

> 见 4.3 节。一句话版：**k 控制融合对排名的敏感度，60 是 RRF 原始论文验证的通用经验值**，衰减温和、平衡两个检索器、避免过拟合调参。

### Q4. 为什么要混合检索（向量 + BM25），只做向量不行吗？

> 向量检索擅长**语义相似**：同义改写、意译、口语化提问都能命中（如"空气污染程度怎么分等级"命中"AQI 分级标准"）。但它是"模糊匹配"，对**精确关键词**不敏感：论文编号、专业术语、型号、数字（如"AQI 大于 300"）这类，向量可能给出语义相近但**不含关键信息**的 chunk。
> BM25 相反：精确抓词，但对"换一种说法"无能为力。
> 两者互补，RRF 融合取并集优势。**这也是业界 RAG 的主流做法**（如 DPR + BM25 混合），我在论文里用消融实验验证了混合 > 单一检索。

### Q5. 为什么用 SSE 流式，不用普通 JSON 返回？

> 1. **体验**：大模型生成要几秒到几十秒，普通请求用户盯着转圈；SSE 逐字输出，用户立刻有反馈；
> 2. **技术**：SSE 基于 HTTP，`text/event-stream`，实现简单、代理穿透好、可断线重连；本项目是服务器→客户端的单向流，SSE 正好；
> 3. **业界一致**：OpenAI/智谱/DeepSeek 的流式接口本身就是 SSE���直接透传语义统一。

### Q6. 为什么用"OpenAI 兼容 API"抽象，而不是绑定某一家？

> 所有大模型平台（智谱、DeepSeek、通义、Kimi、硅基流动、OpenAI）都提供 OpenAI 兼容的 `/chat/completions` 和 `/embeddings` 接口。我的 `LLMClient` / `APIEmbedder` 只依赖这个统一协议，**换模型只改 .env 三行**（BASE_URL / MODEL / KEY），不碰代码。这既让答辩现场可以随时演示"切换供应商"，也是工程上解耦供应商风险的标准做法。
> 这也是毕设加分点：体现了"接口抽象"的软件工程思想。

### Q7. 为什么向量库和 SQLite 双写？怎么保证一致性？

> 两个存储职责不同：ChromaDB 管"向量检索"，SQLite 管"业务元数据"（用户、文档状态、chunk 与 vector_id 的对应、会话、消息）。它们是**两个独立存储，无法用数据库事务**。
> 一致性策略（pipeline.py）：
> 1. **写入顺序：先向量、后元数据**（50 行 add_chunks → 53-63 行写 Chunk 表）——即使中间失败，向量冗余可清理，但元数据不会引用不存在的向量；
> 2. **删除顺序：先删向量、再删记录**（`_purge_doc_from_vector`，78-84 行）；
> 3. **文档级幂等**：重传同文件时先 purge 旧向量再入库；`(kb_id, filename)` 唯一约束兜底（models.py:62）。
> 口径：**双库一致性靠"顺序 + 幂等清理"保证，单侧失败可恢复，不会出现脏引用。**

### Q8. 为什么文档处理是异步状态机（pending→processing→ready/failed）？

> 解析 + 切分 + embedding + 入库是**耗时操作**（PDF 解析 + API 向量化），同步处理会让上传接口阻塞几十秒。设计上：上传接口只落盘 + 建记录（pending），后台同步处理并更新状态，前端轮询文档状态刷新。**失败有 error_msg 可追溯**，这是工程完整性的体现。

### Q9. 为什么要有 hash 伪向量 + echo 双开关？

> 答辩现场最怕**环境起不来**。这两个开关保证：没有网络、没有 API Key 的机器上，系统**依然能完整演示全流程**（上传→切分→检索→融合→流式输出），只是回答是模拟内容。这体现了"演示兜底"的工程意识，也方便无成本开发调试。真实效果由 api 模式提供。

### Q10. 为什么认证用 PBKDF2 + JWT？

> - **密码**：PBKDF2-SHA256、12 万次迭代（OWASP 推荐标准），加盐存储，防彩虹表；绝不存明文。
> - **会话**：JWT（HS256）无状态认证，7 天有效期，前端 localStorage 存 token，请求带 `Authorization: Bearer`。无状态 → 服务可横向扩展、无需服务端会话存储。

### Q11. 为什么前端零依赖（原生 HTML/JS）？

> 1. 毕设评审可读性：无构建流程、无 node_modules，源码直接可运行；
> 2. 稳定：不受前端框架版本影响，答辩现场不怕环境问题；
> 3. 够用：SSE 用 `fetch + ReadableStream` 解析，交互复杂度完全覆盖。
> 如果老师质疑"不够现代"，补一句：**前端不是本项目重点，后端 RAG 管线才是；选零依赖是为了把精力集中在核��算法上。**（这是我主动做的减法。）

### Q12. 检索结果怎么保证"引用可溯源"？

> 三层保障：1) chunk 入库时 metadata 带 `doc_id/page/heading`，检索结果直接携带；2) Prompt 要求 LLM 句末标注 [n]，与参考资料编号一一对应；3) 前端有"引用来源抽屉"，点击 [n] 展开原文片段和页码。**用户能核验每条回答的依据，这是 RAG 相比裸 LLM 的核心价值。**

## 第七部分：高频追问 30 题（含参考答案）

1. **RAG 是什么？和微调的区别？** → 检索增强生成：外部知识检索 → 注入上下文 → 生成。微调是改模型权重；RAG 不改权重、知识可随时增删、成本低、可溯源，适合知识频繁更新的领域问答。
2. **什么是幻觉？RAG 怎么缓解？** → LLM 编造不存在事实。RAG 用检索到的真实资料约束生成 + 强制引用编号，答不出就明说（SYSTEM_PROMPT 第 2 条）。

23. **documents 表的状态机？** → pending→processing→ready/failed，失败记录 error_msg。
24. **向量删除为什么按 id 分批 100？** → ChromaDB 单次删除量限制，100 一批稳妥。
25. **检索评分为什么看排名不看分数（RRF）？** → 两类检索器分数量纲不同不可比；排名是相对序，天然可比。
26. **如果知识库为空会怎样？** → 检索返回空 → Prompt 里"（无参考资料）" → LLM 按系统提示答"根据现有资料无法回答"。
27. **你的系统怎么测试的？** → tests/smoke_test.py 端到端 9 项断言：健康检查/注册登录/建库/上传解析/问答/会话/消息/统计，幂等可重复跑。
28. **hash 向量模式下检索结果靠谱吗？** → 不靠谱（仅供流程验证）；真实效果必须 api 模式 + bge-m3。这是双模式的边界，答辩要主动说清楚。
29. **你的系统创新点是什么？** → 1) 自主实现 RAG 管线（不依赖框架）；2) 混合检索 + RRF 融合；3) 针对学位论文类文档的噪音过滤策略（点号密度 + 关键词前缀）；4) 双模式设计保证任何环境可演示；5) OpenAI 兼容抽象，供应商无感切换。
30. **和市面上 RAG 框架（LangChain）比，你的劣势？** → 生态和功能广度不如；但核心链路自主实现，原理吃透、代码可控、无黑盒，契合毕设"研究学习"目标。

## 第九部分：LoRA 工作量 → 论文「技术预研」章节（不浪费）

> 思路：第二章（技术预研）写你**系统性尝试过微调路线**，形成"尝试 → 分析 → 决策"的完整论证链条，这本身就是研究过程，答辩加分。

### 2.x 大模型领域化技术路线分析（建议小节标题）

**直接可用的段落（按你实际情况改写）：**

> 针对垂直领域知识问答任务，大模型领域化主要有两条技术路线：**参数微调（Fine-tuning / LoRA）**与**检索增强生成（RAG）**。为确定最终方案，本文对两条路线进行了预研对比。

> **（一）LoRA 微调路线尝试。** 低秩适配（LoRA）通过在冻结的预训练模型权重旁注入低秩矩阵实现参数高效微调。本文早期实验中尝试了 LoRA 微调路线：选取开源基座模型，基于领域问答数据集构造指令微调样本，配置 LoRA 秩参数（r=8）、缩放系数（alpha=16）与学习率进行训练尝试。预研结果表明该路线存在三个现实瓶颈：
> 1. **数据量不足**：LoRA 微调效果高度依赖高质量领域指令数据，本文可获得的标注问答样本仅百余条，远低于微调所需的下限，存在过拟合风险；
> 2. **评估闭环缺失**：微调效果需要专业评测集与人工评估才能量化，在无 GPU 环境下逐轮实验迭代成本高、周期长，难以形成"训练-评估-迭代"闭环；
> 3. **知识更新困难**：微调后知识固化在权重中，领域知识更新需重新训练，无法满足知识库动态增长的场景需求。

> **（二）RAG 路线选型。** 检索增强生成通过外部知识检索为生成提供实时依据，具有无需训练、知识可增量更新、回答可溯源三大优势，与"领域知识持续积累"的应用场景高度契合。经预研对比，本文最终选择 **RAG 作为系统技术路线**，并在后续章节中详细阐述其架构设计与实现。微调路线的预研结论（数据瓶颈与评估瓶颈）为 RAG 方案中的检索质量优化与引用溯源机制设计提供了需求依据。

**答辩话术**（被问"为什么不做微调"）：
> "我确实先尝试了 LoRA 微调路线（论文 2.x 节有完整预研）。预研结论是三个瓶颈：数据量只有百余条带标注样本，微调容易过拟合；没有专业评测集和 GPU，无法形成训练-评估闭环；而且知识更新要重新训练，和我的应用场景（知识库动态增长）冲突。RAG 不需要训练、知识实时可更新、回答带引用可溯源，所以在预研阶段就明确了 RAG 方向。这也是论文第二章的选型依据。"

### 如何把 LoRA 实验痕迹变成论文资产

- 如果留了训练脚本/日志：放到论文附录"预研实验记录"，正文一句话引用；
- 如果完全没留：只写"预研分析"（对比表格 + 结论），**不要编造实验数据**——答辩老师追问细节时诚实说"预研以文献调研和基线实验分析为主"即可；
- 对比表格建议（答辩可讲）：数据需求 / 硬件需求 / 知识更新 / 可溯源 / 开发周期，五维度 LoRA vs RAG。
